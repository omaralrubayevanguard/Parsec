# Parsec 17 · how this tree was made from Parsec 16.3, and how it was proven

## Before

Parsec 8 was one hand-written HTML file. Parsec 9 to 16.3 were built by `build12.py`: it took the Parsec 8 file, inserted the page modules, and ran **61 patch files making 723 find-and-replace edits** over them, then pruned what nothing could reach, then assembled and pruned the CSS. A build took about four minutes; a change often meant patching a patch; two people (or two chats) working at once collided on anchors; and the only source of truth that actually ran was the 8 MB output.

## What was done

1. **The 16.3 build was taken apart** with a parser (`tools/migration/extract.js`): the page skeleton, each `<style>` block, the three other scripts, and the app script's 2,774 top-level statements — plus the inner statements of the 17 page closures (`JC`, `CX`, `TL`, `PT`, …).
2. **Every statement was assigned to a file by area** (`tools/migration/emit.py`, the `MAP` and `INNER` tables), cut exactly at statement boundaries so comments travel with the code they describe. 2.6 MB of truck pictures became 112 `.webp` files in `assets/trucks/`; the RO page's 470 KB stylesheet string became `styles/ro-page/*.css`; the 713 KB page stylesheet was split at the pieces each version had appended (`styles/app/`).
3. **The load order was kept exactly.** Function declarations are hoisted, so where a function lives doesn't matter; the order of what runs at load does (constants, page closures, 222 listeners — 20 of them capture-phase `keydown` handlers that take precedence by registration order — 40 wrappers, init). `build/manifest.txt` lists the files in the original order; `build/order-baseline.json` records the sequence; the build refuses a change.
4. **A new build** (`build.py`) joins the files, fills the markers, runs the guards, and writes the app and the test build in about two seconds.
5. **Headers** on all 261 files (purpose and flow by hand in `tools/purposes.json`; facts generated by `tools/headers.py`), headers on every stylesheet, and the docs.
6. The version line moved to `src/app/kit/version.js` (the one deliberate load-order change, accepted).

## The proof

`tools/migration/compare.js old.html new.html` compares the two files ignoring comments and whitespace:

- the HTML around the blocks, and the same blocks in the same order;
- every `<style>` block as normalized CSS;
- the RO engine and the two QR libraries token by token;
- the app script: the **set** of 2,084 top-level function declarations (each identical, token by token, string *values* compared) and the exact **sequence** of the 690 load-time statements.

Result on the day of the migration: `SAME: the new build means exactly what the 16.3 file means.` (Run it again any time against `Parsec_16.3.html`; after Parsec 17 the version line is the one expected difference.)

Then the whole test suite (113 scripts, `tests/run.py`) was run against both builds; the pass/fail picture is the same (the handful of old scripts that fail do so on 16.3 too — see `tests/RESULTS-17.md`).

## Kept for the record

`tools/migration/` has the three one-time tools. They are not part of the build and are not needed again; they document how the cut was made, which is useful when something in the layout looks arbitrary (it usually is the position a patch happened to insert it at).
